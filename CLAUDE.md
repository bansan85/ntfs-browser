# CLAUDE.md

This file guides Claude Code when working with code in this repository.

## Project overview

`ntfs-browser` is a C++20 library, Windows-first. It parses NTFS volumes directly: raw disk and MFT structures, not filesystem APIs. It is a modernized, read-only rewrite of the old CodeProject "An NTFS Parser Lib" (BSD-3c).

## Build

Windows and MSVC are the primary target. The MFC demo apps, the `NtfsDir2` console sample and `NtfsFuzzer` are Windows-only; the Catch2 unit tests, `NtfsDir`, `NtfsMftList`, `NtfsCompare` and `NtfsFuzzerAfl` build and run on Linux too (see the GCC/Linux paragraph below). The build requires submodules (`3rdparty/gsl`, `3rdparty/Catch2`, `3rdparty/spdlog`, `3rdparty/cryptopp`, `3rdparty/cryptopp-cmake`, `3rdparty/frozen`). Clone with `--recurse-submodules`, or run `git submodule update --init --recursive`.

```
cmake -S . -B build
cmake --build build --config Debug --parallel
```

An existing configured `build/` directory (Visual Studio generator) is already present in this repo. You can also open `build/NtfsBrowser.slnx` in Visual Studio.

[CMakePresets.json](CMakePresets.json) defines the presets: `static`, `shared`, `static-vcpkg`, `shared-vcpkg`, and the reduced-feature ones. These name no generator, so each takes the platform default: Visual Studio on Windows (multi-config, build preset defaults to Debug, no `compile_commands.json`), and the CMake default on Linux (pass `-G Ninja`). Two more presets, `vs2022-amd64` and `vs2026-x86`, name a Visual Studio generator and an architecture. Each builds into `build/<preset>/`. The workflow presets (`cmake --workflow --preset <name>`) cover `static`, `shared`, the two vcpkg presets and the reduced-feature ones. VS Code uses them (`cmake.useCMakePresets`). The `*-vcpkg` presets point `CMAKE_TOOLCHAIN_FILE` at a vcpkg checkout next to the repository (`${sourceDir}/../vcpkg`).

```
cmake --preset static
cmake --build --preset static --parallel
```

`BUILD_SHARED_LIBS` (default OFF) selects a static or shared `NtfsBrowser` lib. spdlog follows it, and is linked PRIVATE: it appears in no public header the library includes. The one public header that includes it, [include/ntfs-browser/log/spdlog-adapter.h](include/ntfs-browser/log/spdlog-adapter.h), is opt-in and header-only (see Logging). Crypto++ (`cryptopp-cmake` over `3rdparty/cryptopp`) does not follow it: it is always static, and linked PRIVATE too. On MSVC the root [CMakeLists.txt](CMakeLists.txt) works around two Crypto++ 8.9 problems: MASM object directories the Visual Studio generator does not create, and `stdext` iterators the newest MSVC STL dropped ([cmake/cryptopp-stdext-compat.h](cmake/cryptopp-stdext-compat.h)).

`NTFS_BROWSER_USE_INSTALLED_{GSL,FROZEN,CATCH2,SPDLOG,CRYPTOPP}` each link an installed copy instead of the submodule. All five default ON under the vcpkg toolchain ([vcpkg.json](vcpkg.json)), OFF otherwise. `NTFS_BROWSER_ENABLE_TESTING` defaults ON only in a top-level build, not under FetchContent.

`NTFS_BROWSER_BUILD_MFC_APPS` (default ON, Windows only) builds the three MFC demo apps (`NtfsAttr`, `NtfsDump`, `NtfsUndel`). clang-cl cannot build MFC: set it OFF there. Their `*Core` libraries still build, since the unit tests link them.

Three feature options, all ON by default, compile code in or out: `NTFS_BROWSER_ENABLE_DECOMPRESSION` (LZNT1), `NTFS_BROWSER_ENABLE_EFS_CRYPTOPP` and `NTFS_BROWSER_ENABLE_EFS_BCRYPT` (the two EFS cipher backends). Turning one off drops its sources, its link dependency and its call sites. Each reaches C++ as a same-named macro, PRIVATE to the library and mirrored on `NtfsBrowserTests`. A `.cpp` or a `src/*.h` tests it with `#if`. A public header MUST NOT: consumers never see these macros. The BCrypt macro is defined on Linux too, so code MUST pair it with `_WIN32`. `NTFS_BROWSER_EFS_MASTER` (CMake) means at least one EFS backend is compiled in. It gates the backend-agnostic EFS sources and the EFS tests. C++ spells the same condition `defined(NTFS_BROWSER_ENABLE_EFS_CRYPTOPP) || (defined(_WIN32) && defined(NTFS_BROWSER_ENABLE_EFS_BCRYPT))`.

Source lists are explicit, not globbed. A new file MUST be added to [src/CMakeLists.txt](src/CMakeLists.txt), the `CMakeLists.txt` of its folder under [NTFSLibTests/unit-tests/](NTFSLibTests/unit-tests/) (one folder per library namespace, see Tests), [NTFSLibTests/tools/fake-image/CMakeLists.txt](NTFSLibTests/tools/fake-image/CMakeLists.txt), [NTFSLibTests/tools/disk-readers/CMakeLists.txt](NTFSLibTests/tools/disk-readers/CMakeLists.txt) or [NTFSLibTests/tools/device-access/CMakeLists.txt](NTFSLibTests/tools/device-access/CMakeLists.txt), inside the matching feature gate if it has one.

CI ([.github/workflows/cmake.yml](.github/workflows/cmake.yml)) builds Debug and Release, static and shared, on `windows-latest`, plus a Debug x86 leg on `windows-2025-vs2026` (preset `vs2026-x86`). The Windows legs use the presets' Visual Studio generator and name the configuration on build and `ctest`. Two Linux legs, GCC and Clang (preset `efs-cryptopp-only`), pass `-G Ninja`. It also builds each reduced configuration once: one feature option off, or both EFS backends off. Every leg runs `ctest`. A `test-data` job first fetches the corpus images on Ubuntu into a cache, which each Windows leg restores. A second job builds [fetchcontent-consumer/](fetchcontent-consumer/): a separate project that pulls this repo in through FetchContent, shared, with every feature ON. Two more workflows run only when triggered manually (`workflow_dispatch`): [iwyu.yml](.github/workflows/iwyu.yml) runs include-what-you-use (clang 23) and uploads a fix patch (IWYU only checks a header next to a `.cpp` of the same stem, so [iwyu-header-stubs.py](.github/scripts/iwyu-header-stubs.py) generates a one-line stub `.cpp` for each other header); [sanitizers.yml](.github/workflows/sanitizers.yml) runs [.github/scripts/san-builds.sh](.github/scripts/san-builds.sh) (clang sanitizer builds, x64 and x86) and uploads its logs.
The `NtfsBrowser` library itself, the `NtfsFuzzerAfl` target ([NTFSLibTests/fuzz/](NTFSLibTests/fuzz/)), the `NtfsDir` and `NtfsMftList` samples ([NTFSLibTests/examples/](NTFSLibTests/examples/)), the `NtfsCompare` tool ([NTFSLibTests/tools/ntfscompare/](NTFSLibTests/tools/ntfscompare/), with a `/proc/mounts` implementation on Linux), and the Catch2 unit tests ([NTFSLibTests/unit-tests/](NTFSLibTests/unit-tests/)) also configure and build on Linux with plain GCC: `cmake -S . -B build-linux && cmake --build build-linux --parallel`, checked with GCC 15 under WSL. `include/ntfs-browser/win-types.h` shims the handful of Windows typedefs (`BYTE`, `DWORD`, `LARGE_INTEGER`, ...) that the on-disk struct layouts and the public API are expressed in; unit-test-only helpers (`fake-ntfs-image.h`, the fake `IDiskReader`s) use the same shim instead of `<windows.h>` directly. Real Win32 API usage — `Win32DiskReader`, drive-letter/path-based `NtfsVolume`/`FileReader` construction, and the child-process spawning `log/logging-child-process-tests.cpp` needs to drive `NtfsFuzzerAfl` — is `#ifdef _WIN32`-guarded out. [NTFSLibTests/unit-tests/support/child-process.h](NTFSLibTests/unit-tests/support/child-process.h) is that spawning code's cross-platform seam: `CreateProcess` on Windows, `posix_spawn` on other platforms, behind `RunProcessToFiles()`. A handful of individual `TEST_CASE`s stay `_WIN32`-guarded where the behaviour itself is Windows-only (the wide `Log::ParseOption()` overload, the ANSI-code-page test). Everything else — the MFC demo apps, the `NtfsDir2` console sample and the clang-oriented `NtfsFuzzer` — stays Windows-only. CMake skips them (`if(WIN32)`) on other platforms.

`NtfsDir` and `NtfsMftList` take a device or an image file on Linux: `ntfsdir /dev/sda1/Windows`, `ntfsmftlist ./disk.img`. On Windows they still take a drive letter, and now an image file too (`ntfsdir c:\image.img\Windows`). The static library `NtfsDeviceAccess` ([NTFSLibTests/tools/device-access/](NTFSLibTests/tools/device-access/), namespace `NtfsDevice`) holds what the three tools share: the `pread` reader `PosixDeviceDiskReader`, `SplitDeviceTarget()` (the longest leading part of the target that is an image file or a block device, the rest being the directory), UTF-8 and wide text conversion, local-time conversion, the argv adapter that gives a POSIX `main()` the wide argv a `wmain()` has, and `Output` ([output.h](NTFSLibTests/tools/device-access/output.h)), the buffered listing that `NtfsMftList` and `NtfsDir` print through: a double buffer, and a writer thread that writes each chunk of 1 MiB while the next is built. Names print as UTF-8 on Linux. On Windows `Output::AppendText()` converts a name as `fprintf("%ls")` did, through the CRT locale: a name that the code page cannot hold stops at its first character that does not fit. The library returns file times in UTC off Windows, so the samples convert them to the host's local time.

## Tests

Tests use Catch2 (vendored under `3rdparty/Catch2`). CTest registers them via `catch_discover_tests`.

```
cmake --build build --config Debug --target NtfsBrowserTests --parallel
ctest --test-dir build -C Debug
```

`ctest -R <regex>` runs the tests whose name matches. A Catch2 tag or wildcard needs the binary itself (`build/<preset>/NTFSLibTests/unit-tests/NtfsBrowserTests.exe` in a preset tree). There, a `[` inside a test name starts a tag: escape it as `\[`.
```
build/NTFSLibTests/unit-tests/Debug/NtfsBrowserTests.exe "<test name>"
build/NTFSLibTests/unit-tests/Debug/NtfsBrowserTests.exe "[efs]"
build/NTFSLibTests/unit-tests/Debug/NtfsBrowserTests.exe "LZNT1*"
```

Test sources live in [NTFSLibTests/unit-tests/](NTFSLibTests/unit-tests/): one folder per library namespace (`alloc`, `attr`, `cache`, `data`, `record`, `io`, `mft`, `volume`, `upcase`, `utf`, `log`, `efs`, `lznt1`, `usn`, `util`), plus `corpus` (forensic images), `fuzz-regression`, `device-access` (the `NtfsDeviceAccess` tools library), `ntfscompare` and `support` (helpers shared by every folder: log sink, child process, MD5, scan comparison). Each folder has its own `CMakeLists.txt` that feeds the one `NtfsBrowserTests` executable, and applies a feature gate per file. A test goes in the folder of the namespace it exercises. A helper shared by several files of one folder goes in a header beside them. Tests must not touch a real disk. Real-disk paths are covered by the manual [NtfsCompare](NTFSLibTests/tools/ntfscompare/) tool, never by ctest or CI. It lists one folder through `NtfsVolume<FullCache>`, `NtfsVolume<NoCache>` and `MftTree`; the two cache strategies MUST agree, and `MftTree` MUST name the same files. The reference takes the sizes, times and attributes from `MftTree`, i.e. from the `$MFT` records, because the directory index keeps its own copies and NTFS updates them late. The access time is not compared: it changes with each listing, and the Windows API reports the index copy. `--summary` prints the count of differences per field instead of each one. It then lists the same folder through `std::filesystem` and the native API, and diffs both field by field against that reference. It opens the real volume by drive letter on Windows, or by the raw block device behind the mount point on Linux. On Linux it also takes a device path (`ntfscompare /dev/sda1/Windows`): when the device is mounted, it compares the library with the operating system at the mount point. When it is not mounted, it compares the three library listings with each other and skips the operating system. It does not exercise the EFS certificate-store key provider ([key-provider-win.cpp](src/efs/key-provider-win.cpp)), so that code stays untested. Tests build synthetic NTFS images in memory ([fake-ntfs-image.h](NTFSLibTests/tools/fake-image/fake-ntfs-image.h)), using the library's own on-disk struct layouts from `src/data` and `src/attr`. They serve those images through fake `IDiskReader` implementations: [memory-disk-reader.h](NTFSLibTests/tools/disk-readers/memory-disk-reader.h) (random-access, whole buffer in memory) or [sequential-disk-reader.h](NTFSLibTests/tools/disk-readers/sequential-disk-reader.h) (offset-ignoring, chunk-at-a-time). [counting-disk-reader.h](NTFSLibTests/tools/disk-readers/counting-disk-reader.h) wraps either one and records every call, to count the reads of a feature and to check that only reads reach the reader. Prefer extending these fakes over adding new test scaffolding.

The corpus tests are the exception to synthetic images: `corpus/dftt-ntfs-tests.cpp`, `corpus/nps-ntfs1-*tests.cpp` and `corpus/ntfs-samples-*-tests.cpp`. They open forensic image files outside the repo, never a device. [.github/scripts/fetch-test-data.py](.github/scripts/fetch-test-data.py) fetches them into `test-data/`. The `NTFS_BROWSER_TEST_*` CMake cache variables, or same-named environment variables, locate them, through [corpus-test-support.h](NTFSLibTests/unit-tests/corpus/corpus-test-support.h); the README lists them. A test MUST reach its image through `RequireCorpusImage()` and `OpenCorpusImage()`, each given a trace name. When the image is absent they fall back to a recorded trace, and `SKIP` only if the trace is absent too. Under `NTFS_BROWSER_REQUIRE_TEST_DATA`, which CI sets on the Windows legs, an absent image `FAIL`s instead. `ntfs.raw` (64 GiB) and `ntfs_extremely_fragmented_mft.raw` (256 GiB) are never fetched: their tests go through `RequireUnfetchedCorpusImage()`, which never fails. [partition-disk-reader.h](NTFSLibTests/tools/disk-readers/partition-disk-reader.h) serves a whole-disk image, offsetting every read into its NTFS partition.

A trace is the bytes a test read from its image, one read after the other, without their address: `RecordingDiskReader` ([recording-disk-reader.h](NTFSLibTests/tools/disk-readers/recording-disk-reader.h)) writes it, `SequentialDiskReader` replays it. Traces live in [NTFSLibTests/fuzz/data/corpus-traces/](NTFSLibTests/fuzz/data/corpus-traces/), one `<name>.trace` per opened volume, in a subfolder so the fuzz regression test does not take them for crash inputs. A trace only fits the read order of the library that recorded it: after a change to the read path, record them again with `NTFS_BROWSER_RECORD_TRACES=1` and the images present. `NTFS_BROWSER_FORCE_TRACES=1` replays them even when the images are present. The Windows-only EFS test of the NPS corpus has no trace.

`NTFSLibTests/examples/ntfsattr`, `ntfsdir`, `ntfsdump`, `ntfsundel` are older sample/demo apps. `ntfsundel` checks the data state of a freed file before it copies it: the dialog asks first when the data is probably another file's or sits on bad clusters. `ntfsdir` is the simplest: it opens a volume, parses the root `FileRecord`, walks down to a path, and traverses entries with `TraverseSubEntriesWithStanding()`. It prints the `--deleted` marker from the standing the walk hands it, and never reads a record itself. It prints through `Output`. `NTFSLibTests/examples/ntfsmftlist` lists every `$MFT` record through `MftTree`.

## Logging

All library diagnostics go through spdlog (`3rdparty/spdlog`, pinned to v1.17.0), behind the levelled `Log::Trace`/`Log::Debug`/`Log::Info`/`Log::Warn`/`Log::Error`/`Log::Exception` entry points in [src/log/ntfs-common.h](src/log/ntfs-common.h). Every level is always compiled in; filtering is runtime-only. spdlog MUST NOT appear in `include/ntfs-browser/*.h`, except `log/spdlog-adapter.h`, nor in any `src/*.h` the unit tests include.

[include/ntfs-browser/log/log.h](include/ntfs-browser/log/log.h) is the public surface: a `Log::Level` enum, a `Log::Config`, a `noexcept Log::Configure()`, and `Log::ParseOption()` for one `--log` argument.

[include/ntfs-browser/log/sink.h](include/ntfs-browser/log/sink.h) lets a consumer choose where messages go. `Log::ISink` is a backend-neutral destination: `ShouldLog(Level)`, `Write(Level, message)` and `Flush()`, none `noexcept`. `Log::SetSinks()` replaces the library's sinks wholesale, with a braced list or a span; null entries are skipped and an empty set discards every message. `Configure()` is `SetSinks()` over the two built-in targets, which `Log::MakeConsoleSink()` and `Log::MakeFileSink()` also return as sinks, so a consumer can keep them next to its own. `Configure()` and `SetSinks()` replace each other's set. The library keeps a reference to each sink until the next call, and never destroys them at exit: a sink that depends on state which dies earlier MUST be released with `SetSinks({})` first. Every sink call is wrapped, so a sink that throws neither makes a log call throw nor keeps the next sink from the message. `Emit()` works on a copy of the set, so a sink MAY call `SetSinks()` or `Configure()` from `Write()`: the message in flight still reaches the old set, and the sink stays alive until its call returns.

[include/ntfs-browser/log/spdlog-adapter.h](include/ntfs-browser/log/spdlog-adapter.h) is the opt-in spdlog layer: `Log::MakeSpdlogSink()` forwards to a consumer's `spdlog::sink_ptr`, and `Log::MakeSpdlogLogger()` emits through a consumer-owned `spdlog::logger`. It is the only public header that includes spdlog. It is header-only and exports nothing, so it compiles against the consumer's spdlog and only an `ISink` crosses into the library: the two spdlog versions, linkages and `SPDLOG_WCHAR_FILENAMES` settings need not match. The library never includes it.

The console-app executables (`NtfsDir`, `NtfsDir2`, `NtfsMftList`, `NtfsFuzzer`, `NtfsFuzzerAfl`) accept the option; the MFC dialog apps have no command line and do not.

```
--log=<console|file>:<off|error|warn|info|debug|trace>[:<path>]
```

The option MAY be repeated, once per target. It splits on the first two colons only, so `C:\dir\ntfs.log` survives. The path field belongs to the `file` target; without it the file sink writes `ntfs-browser.log` in the current directory.

`Log::Config::file_path` is a `std::filesystem::path`, and the build defines `SPDLOG_WCHAR_FILENAMES`, so on Windows a log path stays wide all the way to `_wfsopen` and is not limited to the active ANSI code page. The four console executables therefore have a `wmain` (`NtfsDir` and `NtfsMftList` have a `main` on Linux, which decodes its UTF-8 argv to wide strings first); `NtfsFuzzerAfl`, which also builds on Linux, picks `wmain`/`main` through `NTFS_FUZZ_MAIN`, and its argv character type is `NtfsFuzz::ArgChar`. `ParseOption()` has a `std::wstring_view` overload on Windows for that wide `argv`, alongside the portable `std::string_view` one.

The console target is split by severity: `error` and `warn` go to stderr, `info`, `debug` and `trace` go to stdout. A message reaches exactly one stream. With no `Configure()` call the console target sits at `warn` and there is no file sink, so a consumer sees warnings and errors on stderr and nothing on stdout.

`NtfsFuzzerAfl` defaults to `--log=console:trace`. The regression corpus in [NTFSLibTests/unit-tests/fuzz-regression/fuzzer-regression-tests.cpp](NTFSLibTests/unit-tests/fuzz-regression/fuzzer-regression-tests.cpp) asserts against the same trace messages, through the test log sink.

Neither the library nor its logging is thread safe, and the built-in sinks are spdlog's single-threaded `_st` variants, so a message takes no lock. `Configure()`, `SetSinks()` and every emitted message MUST come from one thread. A consumer sink shared with other threads MUST take its own lock. A thread-safe sink is the answer if that ever has to change.

A worker thread of the library never reaches a sink: it captures. A `Log::Detail::CaptureScope` ([src/log/ntfs-common.h](src/log/ntfs-common.h)) makes `Emit()` of the calling thread append to a `Log::Detail::CapturedLog`, and `IsEnabled()` answer from the levels that capture was given. Those levels come from `Log::Detail::EnabledLevels()`, which the thread that owns the sinks asks before it starts a worker. A worker MUST NOT ask a sink. The thread that owns the sinks replays a stretch of the capture, between two `CapturedLog::Mark`s, with `Replay()`. Each line goes to the sinks in order, and each sink chooses by level, as it would have. The salvaged conditions the worker counted between the marks join the replaying thread's `RecoveredCount()`, which is per thread. `MftTree` is the one user (see Read path).

The unit tests make a capturing `Log::ISink` the library's only sink before `main()` ([NTFSLibTests/unit-tests/support/test-log-sink.h](NTFSLibTests/unit-tests/support/test-log-sink.h)). A test that calls `Configure()` or `SetSinks()` itself MUST call `InstallCaptureSink()` again afterwards, since both replace the sinks wholesale. `CaptureSinkHandle()` gives the sink to a test that installs it next to one of its own. A test that needs spdlog output builds a sink with `MakeSpdlogSink()`. The `[.benchmark]` case `rejected log calls cost` in `log/rejection-cost-tests.cpp` prints the cost of a rejected message; run it in a Release build to compare a change to the dispatcher.

## Commits

Commit messages follow Conventional Commits, without a scope: `fix:`, `refactor:`, `test:`, `docs:`, `chore:`, `feat:`, `build:`, `ci:`, `style:`, `perf:`. They are written in English. The title starts lowercase after the prefix, has no trailing period, and MUST NOT exceed 50 characters, prefix included. The body wraps at 72 characters. Each commit ends with a `Co-Authored-By:` trailer naming the model that wrote it.

## Writing style

Use short sentences: in code comments and in documentation.

Use RFC 2119 keywords (MUST, MUST NOT, SHOULD, MAY, ...) to state an obligation.

A comment MUST clarify something the code cannot say on its own. A comment MUST NOT narrate what the code already shows.

Every public function in `include/ntfs-browser/*.h` gets a purpose comment. One line, if the function name and every parameter name are self-explanatory. Several lines, if the purpose itself is not obvious. A single parameter can get its own comment, if only that parameter's effect is unclear.

A private method — declared with no public header, or not defined inline — gets the same treatment, in the `.cpp` file where it is implemented.

Every constant (`inline constexpr` in a header, `constexpr` in a `.cpp`) gets a comment: what it is for, and why it has that value.

A `TEST_CASE` (or `SECTION`) MUST NOT get a comment above it. Catch2's own name string is already the description.

Code that is not obvious to a developer reading it gets one comment line, directly on the line before it. This is the only other case where a comment belongs outside a function/constant purpose comment.

A boolean condition needs a comment above it once it combines at least four distinct elements — variables, `sizeof(...)` calls, casts, or literals — across more than one kind of check (eg. bounds arithmetic, a width cast, a sentinel/terminator comparison). Fewer than four elements does not meet this bar, even if the condition spans multiple lines for formatting reasons only. The comment states what the condition MEANS (the invariant it enforces), not what each term computes. One line normally; two lines if the condition's own complexity or length needs it.

Skip the comment entirely if a trace/logging call inside the same branch already states, in its own message, what the condition rejects.

## Architecture

### Strategy-templated core

Almost every core class is templated on `Cache::Strategy` ([include/ntfs-browser/cache/strategy.h](include/ntfs-browser/cache/strategy.h)): `Strategy::NoCache` or `Cache::Strategy::FullCache`. This propagates through `NtfsVolume<S>` → `FileReader<S>` → `FileRecord<S>` → `AttrBase<S>` and all `Attr*<S>` subclasses. `FullCache` keeps the 64 KiB blocks it read in a bounded LRU block cache (`Cache::BlockCache`, [src/cache/block-cache.h](src/cache/block-cache.h)), one heap allocation per block. `NoCache` re-reads and returns views into a short-lived buffer instead. Attributes under `NoCache` hold raw pointers or spans into that buffer. Callers MUST NOT assume attribute data outlives the next read. Under `FullCache`, `NtfsVolume::Read()` returns a `Cache::View` ([include/ntfs-browser/cache/view.h](include/ntfs-browser/cache/view.h)) that owns its bytes through a `shared_ptr`: a block a view still holds is never freed. `NoCache` has no view, and `Cache::ReadResult<S>` picks the right type. A caller that keeps `FullCache` bytes beyond one statement MUST keep the `View`, since converting it to a bare span gives up the owner. Pick the strategy that matches lifetime needs when writing code that touches these templates.

### Templates and symbol export

Class templates are declared in headers and defined in `src/*.cpp`. Each `.cpp` ends with explicit instantiations for both strategies (`template class FileRecord<Cache::Strategy::NoCache>;`, then `FullCache`). A new class template, or a new member function template, MUST be instantiated there too, or it will not link. Most concrete attribute wrappers also take their base class as a parameter: `AttrFileName<AttrResidentNoCache, Strategy::NoCache>`. `AttrList` and `AttrBitmap` exist over both a resident and a non-resident base.

A template whose only parameter is a `Cache::Strategy` has exactly two instantiations. A header MUST NOT define any function of it, member functions, free functions and lambdas included: it declares them, and the `.cpp` defines them. A type alias, a `static_assert`, a constant, and a `= default` or `= delete` member MAY stay in the header. A template with another parameter (a base class such as `Resident`, a callable, a parameter pack) is exempt. [check-strategy-templates.py](.github/scripts/check-strategy-templates.py) enforces this, run by [format.yml](.github/workflows/format.yml); its `--self-test` option runs the built-in samples.

A shared build exports symbol by symbol. `generate_export_header` writes `NTFS_BROWSER_EXPORT` into `src/include/ntfs-browser/export.h` in the build tree. A public class or function that crosses the DLL boundary carries it. An internal symbol the unit tests reach through a `src/` header carries `NTFS_BROWSER_EXPORT_TESTS_ONLY` ([src/internal-export.h](src/internal-export.h)) instead. It exports only under `NTFS_BROWSER_EXPORT_INTERNALS_FOR_TESTS`, which the unit tests' CMakeLists defines on the library. The class-level macro does not reach a member function template: each explicit instantiation of one repeats it. A test that calls a new internal symbol links in a static build, but fails in a shared one until that symbol is marked.

### Hidden state (pimpl)

`NtfsVolume<S>`, `FileRecord<S>` and `MftTree` keep every data member and private method behind a private nested `Impl`, reached through `impl_`. A public header MUST NOT declare a data member or a private method for these classes: add it to `Impl`.

`NtfsVolume<S>::Impl` and `FileRecord<S>::Impl` are defined in [src/ntfs-volume-impl.h](src/ntfs-volume-impl.h) and [src/io/file-record-impl.h](src/io/file-record-impl.h), since more than one `.cpp` needs them. `MftTree::Impl` is defined in [src/mft-tree.cpp](src/mft-tree.cpp). An `Impl` is not exported, and no accessor gives it out: only its own class names it. Another library class gets what it needs through a method of `NtfsVolume<S>` or `FileRecord<S>` that forwards to the `Impl` (`NtfsVolume<S>::ReadMftSlots()`, `FileRecord<S>::SetBypassDeletedGate()`, `FileRecord<S>::ImportAttrListEntry()`, ...). Logic that works mostly on that state moves into the owning class, instead of being served by one accessor per field. `AttrParser` ([src/io/file-record-attrs.h](src/io/file-record-attrs.h)) is a nested class of `FileRecord<S>::Impl` and fills its attribute lists, while `DirectoryIndex<S>` and `AttachEfsContext()` use only `FileRecord<S>`'s public API.

No class is a C++ `friend` of another: `include/`, `src/` and `NTFSLibTests/` MUST NOT contain a `friend` declaration. A class that needs a private method of another makes it a public method of an internal (`src/`) class, or a narrow public method of the owner. [.github/scripts/check-no-friend.py](.github/scripts/check-no-friend.py) enforces this, run by [format.yml](.github/workflows/format.yml).

`FileRecord<S>::Impl::self_` points back at the owning `FileRecord`. The move constructor MUST repoint it. `Filename`, `IndexEntry` and `AttrBase<S>` stay plain: they hold two or three members, are copied per index entry or read on the hot path, and their subclasses read those members directly.

### Read path / object graph

- `IDiskReader` ([include/ntfs-browser/disk-reader.h](include/ntfs-browser/disk-reader.h)) abstracts "get raw bytes from a backing store" behind `Open()`/`ReadInto()`, and an optional `Size()` (the size of the backing store in bytes, `std::nullopt` by default, or when the store has no fixed size). `Win32DiskReader` is the production implementation: a real disk/device handle, or a plain file treated the same way via `CreateFileW`. Tests substitute `MemoryDiskReader` or `SequentialDiskReader`. `ReadAheadDiskReader` and `RecordingDiskReader` forward `Size()` to the reader they wrap, without reading. `Prefetch(offset, length)` and `CancelPrefetch()` are hints, ignored by default: they announce the ranges about to be read, in order, and change only when the bytes are read, never which bytes a read asks for. `Win32DiskReader` reads the announced ranges ahead through a second, overlapped handle, at most 32 reads and 64 MiB at once, all on the caller's thread: no worker thread. A read that falls in an announced range is copied from it, and the ranges announced before it are dropped. That handle is buffered like the main one: an unbuffered read of a mounted volume returns what is on the disk, which can lag what NTFS caches by hours. `ReadAheadDiskReader`, `RecordingDiskReader` and `CountingDiskReader` pass the hints on, and `PosixDeviceDiskReader` turns them into `posix_fadvise(POSIX_FADV_WILLNEED)`. `FileReader<FullCache>` widens a hint to whole 64 KiB blocks, and leaves out those its cache holds: a block served from memory is never read, and its range would be read for nothing. The test readers ignore them, so a trace does not depend on them.
- `NtfsVolume<S>` ([include/ntfs-browser/ntfs-volume.h](include/ntfs-browser/ntfs-volume.h)) owns a `FileReader<S>`. It can be constructed from a drive letter, an arbitrary path (device or image file), or an already-open `IDiskReader` (for tests/fakes). It parses the boot sector (BPB) to learn sector, cluster, file-record, and index-block sizes. It then locates and parses the `$MFT` file record itself, through `Mft::MftBootstrap<S>` ([src/mft/mft-bootstrap.h](src/mft/mft-bootstrap.h)), to resolve further file records through possibly-fragmented `$MFT` data runs. Every constructor takes an optional `VolumeOptions` ([include/ntfs-browser/volume-options.h](include/ntfs-browser/volume-options.h)), fixed for the volume's lifetime and read back through `GetOptions()`. The two flags default off. `include_deleted` gates content and visibility: `FileRecord::ParseFileRecord()` still reads a freed record's header (`IsDeleted()` works), but `ParseAttrs()` returns false on it unless this is on. Without it, directory entries that name a freed record, or one reused under another sequence number, are also hidden from listings, name lookups and walks. `recover_errors` chooses, for a damaged file record, index block, cluster run or `$ATTRIBUTE_LIST`, between rejecting it whole (off, the default) and salvaging what parses (on, today's long-standing behaviour). A record that an index entry names but that does not parse is a damaged file record too: hidden when off, returned when on, with its metadata taken from that entry. The two flags are independent: `recover_errors` decides what is found, and `include_deleted` decides which of the found, healthy items are shown. Rejection is one item: the enclosing scan or walk moves on to the next one. A salvageable condition logs Warn when strict and Info when recovering, through `Log::Recoverable()` ([src/log/ntfs-common.h](src/log/ntfs-common.h)). When recovering, a record from 0 to 3 that does not parse in `$MFT` is read again from its copy in `$MFTMirr`, at the BPB's `lcn_mft_mirr` (`FileRecord<S>::Impl::ParseRecord()`, through `NtfsVolume::ReadMftMirrorRecord()`). The copy may be stale. A null, overflowing, out-of-volume or `$MFT`-aliasing `lcn_mft_mirr` means no copy, and rejects nothing. Strict mode never reads it. When recovering, a record whose update sequence check fails on some sectors, and verifies on at least one, is salvaged instead of rejected: `ParseRecord()` patches the sectors that verify, leaves the others as they are (their last two bytes are their own, not the sequence number), and `FileRecord::IsSalvaged()` is true. A salvaged record is untrusted, and a copy in `$MFTMirr` is preferred to it. A record that does not carry the FILE signature (a `BAAD` one included), and a record with no sector that verifies, is never salvaged. Strict mode rejects every one of them. When recovering and sector 0 is unusable (the read fails, or the parse rejects it), `NtfsVolume<S>::Impl::UseBackupBootSector()` looks for the backup boot sector NTFS keeps in the last sector of the volume. It needs `IDiskReader::Size()`: without a size, or under 512 bytes, there is no fallback. For each sector size of 512, 4096, 1024 and 2048 that divides `Size()`, it reads the last `size` bytes straight from the reader, bypassing the block cache. It adopts the first copy that parses and declares that same sector size. The last sector of the backing store is the backup only if the file system fills the whole store: a partition larger than its file system shifts it, and the fallback then finds nothing. Strict mode never calls `Size()`. The volume's own metadata reads ($Volume, `$MFT`'s record, and the extension records `MftBootstrap` opens for `$MFT`'s continuations) bypass the `include_deleted` gate, so a freed `$MFT` or `$Volume` record doesn't take the whole volume down. The third option, `max_cache_bytes`, is the soft ceiling of the `FullCache` memory, per volume (`NoCache` ignores it). It defaults to `Cache::default_max_cache_bytes` (256 MiB), and `Cache::unlimited_bytes`, the largest value, removes the limit. After each read, and when the last view of a block is dropped, the cache frees the fewest unused blocks needed to get back under it, least recently used first. A block a view holds stays, so the total can exceed the ceiling while such views live. 0 frees a block as soon as its last view is dropped. The cache logs nothing about eviction. `NtfsVolume::GetCacheStats()` reports `held_bytes` and `in_use_bytes`, and `MinifyCache()` frees every block no view uses. A stitched buffer (a read that spans blocks, or one that bypasses the cache) belongs to its view alone and counts as in use. The cache is single-threaded, dropping a view included. The fourth option, `read_ahead_bytes`, is off at 0. Set, it wraps the volume's reader in `Io::ReadAheadDiskReader` ([include/ntfs-browser/io/read-ahead-disk-reader.h](include/ntfs-browser/io/read-ahead-disk-reader.h)): after two back-to-back reads, a worker thread inside the decorator keeps two chunks of that size queued ahead. The caller still MUST use the volume from one thread. The reader MUST support random access, so `SequentialDiskReader` does not fit. The fifth option, `max_usn_records`, is the most records of the change journal the volume keeps (see below). It defaults to `Usn::default_max_records`, 1 638 400: a journal of 100 MiB holds at most that many, since the smallest record takes 64 bytes, so it never truncates one. In general a journal holds at most its maximum size / 64 records. `Usn::unlimited_records` removes the limit, and 0 keeps none.
- `FileRecord<S>` ([include/ntfs-browser/io/file-record.h](include/ntfs-browser/io/file-record.h)) represents one MFT file record. `ParseFileRecord(fileRef)` reads it. `ParseAttrs()` walks and instantiates its attributes; an optional `Mask` can skip unwanted attribute types. Set the mask before parsing, to avoid wasted work. When recovering, an attribute that fails to parse is skipped and the walk goes on after it, since its header is sound: its length is at least a header and inside the record, and says where the next attribute starts. A header whose length is not sane still ends the walk, and so does a missing end marker. Either way `ParseAttrs()` returns false, as it always did when an attribute was lost, and keeps the attributes that parsed, those after the lost one included. Strict mode stops at the first attribute that fails and drops them all. Directory traversal (`TraverseSubEntries`, `FindSubEntry`) walks `$INDEX_ROOT`/`$INDEX_ALLOCATION` B-tree index entries. This includes index entries that only reach a file via `$ATTRIBUTE_LIST`: a record's attributes can be split across an extension record.
- Batched directory walk: `FileRecord::TraverseSubEntriesWithStanding()` is `TraverseSubEntries()` with its probes batched and their outcome handed to the callback. It is opt-in: `TraverseSubEntries()` reads, logs and calls back exactly as it always did, and the fuzz corpus and the recorded traces depend on it, since they replay bytes and ignore addresses. Both walks go through `DirectoryIndex<S>::Walk()`, with a `WalkTarget<S>` that names the callback and, for the batched walk, an `Io::EntryProber<S>` ([src/io/entry-prober.h](src/io/entry-prober.h)). Each entry still gets `IsHiddenGiven()`, the decision of `IsEntryHidden()`, so the same entries show in the same order. The callback also gets an `Io::RecordStanding` ([include/ntfs-browser/io/record-standing.h](include/ntfs-browser/io/record-standing.h)): `Live`, `Deleted` (freed), `Reused` (in use under a sequence number the entry does not name; an entry that names 0 claims none) or `Unreadable`. A group is one index node: the root, a block, an orphaned block. Before the walk delivers the entries of a node, the prober probes their records together: sorted by slot, a hole of up to 64 KiB of `$MFT` between two of them read across, a run of up to 1 MiB, the runs announced to the reader (`NtfsVolume::PrefetchMftSlots()`), read with `NtfsVolume::ReadMftSlots()`, then parsed from memory with `ParseFileRecord(ref, bytes)`. A round is at most 128 records, and withdraws what nothing read (`CancelPrefetch()`). A record failing its update sequence check is read again by `ParseFileRecord(ref)`, which logs it twice, as the default walk does. A node is never copied: its entries stay valid while the probes read other records, as they do in the default walk, which probes in the middle of a node. The prober keeps a memo of the records it probed, 2^18 at most and emptied when full, so a DOS alias and its Win32 name share a probe, wherever they sit in the index. What a probe logs is captured (`Log::Detail::CapturedLog`) and replayed each time an entry takes the outcome, so the log is the one of probing at the entry; `Log::Detail::ForgetRecoveredSince()` keeps the salvage count from doubling. Only the Trace lines about disk reads differ, and the tests leave them out. `FullCache` announces only the blocks its cache lacks. The fuzz harness runs the batched walk in `ProbeStandingWalk()`, the last probe, since it reads in another order. `NtfsDir` and `NtfsDir2` use it.
- Cluster allocation comes from the volume's `$Bitmap` (MFT record 6), read through its unnamed `$DATA` by `Alloc::ClusterBitmap` ([src/alloc/cluster-bitmap.h](src/alloc/cluster-bitmap.h)), one window of 1 MiB at a time, so a `NoCache` volume never holds the whole bitmap. `NtfsVolume::GetClusterState()`, `GetRangeState()`, `GetRangeStates()` and `GetSpaceSummary()` load it on first use, bypassing the `include_deleted` gate like `$UpCase`, and cache a failure. The bitmap is a snapshot: it is never read again. With `recover_errors` off a damaged `$Bitmap` run list rejects the bitmap, so every answer is `Unknown`. On, the runs that parse are kept and only the clusters past them are `Unknown`. A window whose read fails keeps the bytes it returned, is not read again, and spoils only itself. A positive finding (an allocated cluster) always wins over an error elsewhere in the same range, and one bad window never fails a batch. The volume's cluster count comes from the boot sector and is cut at `IDiskReader::Size()` when known; bytes of bitmap past what those clusters need are never read. `AttrBase::GetExtents()` lists a stream's real runs, and `FileRecord::GetDataState()` folds them into `Intact`, `Reallocated` or `Unknown` for a deleted stream: a hint, not a proof. A live record is `Intact` without any bitmap read. `MftTree` gives each kept entry a `data_state` for its unnamed `$DATA` by default when `include_deleted` is on (`ScanOptions::annotate_data_state` turns it off): the extents of deleted files wait in a buffer of at most 262 144 queries, which one sorted `GetRangeStates()` call resolves, so the scan reads each window of the bitmap once per flush and not once per file. With `recover_errors` on, the first `ReadData()` of a live `$DATA` stream also logs, once, a run that has a free cluster, and once a run that sits on a bad cluster. Strict mode reads neither file then.
- Bad clusters come from the named `$Bad` stream of `$BadClus` (MFT record 8), through `AttrBase::GetExtents()`: the real runs of that sparse stream, by their LCN, are the bad clusters. `Alloc::BadClusterList` ([src/alloc/bad-cluster-list.h](src/alloc/bad-cluster-list.h)) sorts, merges and clamps them to the volume, and `NtfsVolume::GetBadClusters()` gives the result (`Alloc::BadClusters`): null when the list is unusable, an empty list when there is no bad cluster, and `truncated` when recover mode cut it. It loads on first use with the bitmap, bypasses `include_deleted`, caches a failure, logs it once, and is copied out of record 8 so the run list is released. With `recover_errors` off a damaged run list rejects the whole list; on, the runs that parse are kept. A list over 5 242 880 extents (80 MiB, the most a Windows volume with 4 KiB records can hold: 6551 segments of the 256 KiB attribute list, 789 extents each, rounded up) is rejected when strict and cut to its lowest extents when recovering. The parse of the run list before that cap is not bounded: it is the attribute's own, as for every file. `Alloc::ClusterBitmap` takes the list and counts a listed cluster as `Bad` whatever its bit (NTFS marks bad clusters allocated): `ClusterState::Bad` and `DataState::Bad` rank after `Allocated` and `Reallocated`, `RangeQuery::bad_clusters` and `SpaceSummary::bad_clusters`/`bad_bytes` count them apart, and a bad cluster is never counted free. A listed cluster whose bit is clear is logged once per volume. When `$Bitmap` is lost and the list is not, a bitmap with no bits stands in: listed clusters stay `Bad`, the rest are `Unknown`, and there is no space report. A read on a bad cluster is never skipped or zero-filled: the library reports the state and the caller decides. The `NtfsUndel` core ([ntfsundel-core.h](NTFSLibTests/examples/ntfsundel/ntfsundel-core.h)) asks `AssessRecovery()` for the data state before a copy, and the dialog asks the user first for `Reallocated` and `Bad`.
- The change journal, `$UsnJrnl:$J` of `$Extend` (MFT record 11), is read only with `recover_errors` on: strict mode never looks `$Extend` up for it and never reads a byte of it. `NtfsVolume::GetUsnJournal()` ([include/ntfs-browser/usn/types.h](include/ntfs-browser/usn/types.h)) returns the decoded records, `Usn::Journal`, as owned data. It returns null when there is no journal, or when its stream cannot be read at all: that is cached and logged once, at Info, and never retried. It loads on first use, bypassing `include_deleted` like `$UpCase` and `$BadClus`: `FileRecord::SetBypassDeletedGate()` also lets the index of a metadata directory show the entries that name freed records. `Usn::LoadJournal()` ([src/usn/usn-journal-loader.h](src/usn/usn-journal-loader.h)) asks `AttrBase::GetRealRanges()` for the byte ranges of `$J` that hold data, with their offsets and the sparse holes left out, so a sparse head of a terabyte costs no read. It reads each range in chunks of 1 MiB through `Usn::RecordScanner` ([src/usn/usn-record-scanner.h](src/usn/usn-record-scanner.h)), which decodes `USN_RECORD_V2` and `V3`. A V4 record has no name: it is only counted. A record's USN is its own offset in `$J`. After damage the scanner steps 8 bytes at a time, and takes a record again only when its header is plausible and that holds, so a false match in damaged bytes is very unlikely. A damaged stretch is counted in `Usn::Journal::damaged_records`, never thrown. Only the newest `max_usn_records` records are kept, and `truncated` then says so. Times follow the rest of the library: local on Windows, UTC elsewhere. `MftTree` asks the volume for the journal when `recover_errors` is on and its scan completed. The first pass already parses the `$UsnJrnl` record (a name of `$Extend`, record 11, in use): it keeps the clusters of its `$J` stream, and once the scan is read, before the tree is linked, announces them to the reader in pieces of 4 MiB (at most 256), so the disk reads the journal while the link runs. It adds no read, and none changes. The announcements are withdrawn after the load. An entry the journal names, by record number and a sequence of the same generation (`Mft::IsSameRecordGeneration()`), gets a `UsnInfo`: last reason and time, every reason, the deletion time. With `include_deleted` on too, a file that no entry accounts for (its record is gone, was reused, or the reference has 128 bits) is listed in `JournalOnly()`, and `GetJournalPath()` gives its path through a parent it can trust. Journal-only files are not in `Entries()`: `Find()` keeps one entry per record number.
- Record slack: the bytes after a record's attribute end marker can hold stale `$FILE_NAME` structures, for instance the old entries of a resident `$INDEX_ROOT` that shrank. They are carved only with both `recover_errors` and `include_deleted` on, and strict mode never scans them. `FileRecord::CarveSlackNames()` ([include/ntfs-browser/io/file-record.h](include/ntfs-browser/io/file-record.h)) runs `Record::CarveFileNames()` ([src/record/slack-carver.h](src/record/slack-carver.h)) on the record bytes after the fixups, from the marker offset that the last `ParseAttrs()` met (`FileRecord<S>::Impl::end_marker_offset`). It reads nothing from the volume, and gives the same answer for both cache strategies. The carver steps 2 bytes at a time, looks for a name length byte, a namespace byte (0 to 3) and well-formed UTF-16 characters, then checks the fixed fields before them that the slack still holds: a parent that is not record 0 or a number that cannot exist, four times between 1980 and 2100, attribute flags NTFS knows. NTFS writes 4 bytes after the marker word that belong to the live record, so a field that starts before `marker + 8` is never read: it is unknown (`parent_known` or `times_known` false). Such a candidate is `partial`, and needs a name of 5 characters or more. A name with no field left at all must also be plain text. Each distinct candidate is reported once, and a name equal to a live `$FILE_NAME` of the record (same name, same parent when known) is dropped. A `Record::CarvedName` ([include/ntfs-browser/record/carved-name.h](include/ntfs-browser/record/carved-name.h)) is a candidate, never a fact, and changes no live field. `MftTree::Entry::carved_names` and `ScanStats::carved_names` hold them. The leftovers of real volumes are plentiful: the `$Extend` record keeps `$RmMetadata`, and a real `$MFT` such as the NIST hacking case gives many old directory entries.
- Index slack: a valid `$INDEX_ALLOCATION` block keeps the entries NTFS moved up to close a gap in its unused space, after the end entry. `FileRecord::CarveIndexSlackNames()` returns them as `Record::CarvedName` candidates (`source` is `CarveSource::IndexSlack`), apart from `TraverseSubEntries()`, which is unchanged. Like the record slack, it needs both `recover_errors` and `include_deleted`, and strict mode returns nothing and reads nothing. `DirectoryIndex<S>::CarveSlackNames()` ([src/io/file-record-index.cpp](src/io/file-record-index.cpp)) walks the blocks like the orphan scan (same plan, same `max_orphan_scan_blocks` cap, a block `ParseIndexBlock()` rejects is skipped). `Attr::IndexBlock::UsedEnd()` gives where the used part ends, set only when every entry parsed clean up to the end entry: a block with a defect that recovery let pass has no slack. The bytes after it, fixups removed, go to `Record::CarveFileNamesFrom()`, which shares the scan of `CarveFileNames()` but trusts nothing before the slack. A candidate is kept only when its parent reference names this directory (sequence rule of the orphan scan), so a name whose parent bytes the end entry overwrote is dropped. A name equal to a live entry of the root or of any block, or already found, is not repeated. At most about a million candidates are kept. The `$INDEX_ROOT` has no slack: its value ends where its entries do. The three Zimmerman `$I30` states give exactly the documented live counts (50, 20, 10) and deleted names (10, 21, 24, DOS aliases left out); Zimmerman's own totals (88, 62, 57) cannot be rebuilt and are not asserted. The `index_slack_*` fuzz inputs come from the hidden test case `write the index slack fuzz inputs`.
- Names collate through the volume's `$UpCase` table (MFT record 10), never through the process locale. `NtfsVolume::GetUpCaseTable()` ([src/upcase/upcase.h](src/upcase/upcase.h)) loads it on first use, bypassing the `include_deleted` gate, and caches a failure. When `$UpCase` cannot be read, the built-in Unicode simple uppercase mapping stands in. `FileRecord::FindSubEntry()` then also scans every entry when the ordered search finds nothing, since that mapping can disagree with the volume's own.
- `AttrBase<S>` ([include/ntfs-browser/attr/base.h](include/ntfs-browser/attr/base.h)) is the base for all attribute wrappers (`AttrResident`, `AttrNonResident`, and the concrete `Attr*` types in `src/`, e.g. `attr-file-name`, `attr-index-root`, `attr-std-info`, `attr-list` for `$ATTRIBUTE_LIST`). Resident and non-resident attributes differ in how `GetData()`/`ReadData()` fetch bytes: inline in the record, versus following data runs through clusters.
- Attribute-level compression (`FILE_ATTRIBUTE_COMPRESSED`) is handled inside `AttrNonResident<S>`. A non-zero `comp_unit_size` in the attribute header makes it read each compression unit's real and sparse runs and LZNT1-decompress it through [src/lznt1/decompress.h](src/lznt1/decompress.h). `ReadData()`/`GetData()` therefore return plain bytes either way, and callers never see a compression unit. Decompression is read-only: nothing re-compresses.
- EFS encryption (`FILE_ATTRIBUTE_ENCRYPTED`) is decrypted inside `AttrNonResident<S>::ReadVirtualClustersRaw()`. After `ParseAttrs()`, `FileRecord<S>` reads the `$EFS` stream (a `$LOGGED_UTILITY_STREAM`, non-resident on a real volume) and gives every `$DATA` stream whose header flag has 0x4000 a shared `Efs::Context` ([src/efs/efs-context.h](src/efs/efs-context.h)). The context resolves the FEK once, on the first read, through an `Efs::IEfsKeyProvider` ([include/ntfs-browser/efs/efs.h](include/ntfs-browser/efs/efs.h)). A failure is cached too. Decryption runs on the copy in the caller's buffer, per 512-byte sector: AES, 3DES or DESX in CBC mode, with an IV derived from the sector's stream offset. It MUST NOT run on the span `ReadClusters()` returns, since under `FullCache` that is the shared ciphertext. Sparse runs are not decrypted. Crypto++ or BCrypt runs the cipher, chosen per volume by `NtfsVolume::SetEfsCipherBackend()`. Crypto++, spdlog and `<windows.h>` MUST NOT appear in a public header, nor in a `src/*.h` the unit tests include. The provider comes from `NtfsVolume::SetEfsKeyProvider()`. When none was set, the first decryption creates one over `CurrentUser\My`. `SetEfsKeyProvider(nullptr)` disables decryption. A test MUST call it, and MUST NOT reach the real certificate store. Only AES-256 is checked against real data. The 3DES and DESX IV word (`0x169119629891ad13`) and the DESX key expansion (128-bit FEK, MD5 with two salts) follow ntfs-3g and are not checked against a real file. DESX runs on Crypto++ only. Read-only: nothing encrypts.
- `MftTree` ([include/ntfs-browser/mft/tree.h](include/ntfs-browser/mft/tree.h)) rebuilds the whole namespace without directory indexes. It reads every `$MFT` record once, and links each record under the parents its own `$FILE_NAME` attributes name. The scan reads `$MFT` in blocks of 4 MiB through `Mft::SlotReader<S>` ([src/mft/slot-reader.h](src/mft/slot-reader.h)), not one record at a time: it cuts a block into records in memory and hands each to `FileRecord<S>::Impl::ParseRecord()`. A slot it does not serve (below `Mft::Idx::User`, outside its plan, or in a block whose read failed) goes through `ParseFileRecord()` as before. The scan gives it the whole plan up front: the ranges of used slots from `$MFT`'s `$BITMAP`, a gap of up to 64 free slots kept inside a range. Each range is cut into blocks from its first slot's cluster on, whatever slots are asked for, and the blocks after the current one are announced to the reader (`NtfsVolume::PrefetchMftSlots()`, up to 16 MiB ahead), so the disk reads them while the scan parses. A parent reference packs a 48-bit record number and a 16-bit sequence number. It is valid when the sequences match, when it carries sequence 0, or when the parent was freed and its sequence is one more (NTFS bumps it on deletion). Record 5 is always the root, even when its own record is lost. Extension records are skipped: their attributes come through the base record's `$ATTRIBUTE_LIST`. A base record with an `$ATTRIBUTE_LIST` waits for a second pass, its entry kept in place: its extension records then come from memory, not from one disk read per list entry. The scan holds the raw bytes of those base records, and of the extension records they will ask for. An extension record is of use to its base only: one met after a base that does not wait is not held, and one met before its base is held provisionally, then released once that base turns out not to wait (`HeldRecords`, [src/mft/tree.cpp](src/mft/tree.cpp)). The held records share a budget of 1 GiB (128 MiB on 32 bits): a system volume of 5 million slots needs 718 MiB. Past it, a base record waits without its bytes, and an extension record is listed with its base. The second pass reads them again, one waiting base record at a time: the record, then its unheld extension records in one sorted pass (`UnheldExtensions`), then its list. It announces those reads to the reader first, 64 records ahead, through `NtfsVolume::PrefetchMftSlots()`, with the clusters of each non-resident list from its header alone (`FileRecord::AttributeListExtents()`). The reader serves a read from the first 64 ranges it holds and drops the ones before it, so the pass reads exactly what it announced, and restarts the announcements every 1024 records that have reads: most waiting records have none. The first pass also remembers which base record each slot it read names (`SlotBases`, 4 bytes a slot). A record an `$ATTRIBUTE_LIST` names that is not held, and whose slot names another base, is not an extension of that file: `FileRecord::SetBaseSource()` lets `ImportAttrListEntry()` skip it, with the logs and the throw a read would have led to, but no read. A slot the first pass did not read, one below `Mft::Idx::User`, and an extension of the listing record itself keep their disk read. `ScanOptions::threads` sets how many threads parse the first pass and the second: 1 is the code path of one thread, N takes N, and 0 lets the scan choose. With several, `SlotScan` ([src/mft/tree.cpp](src/mft/tree.cpp)) asks the reader for each window with `SlotReader::ServeWindow()`, at the moment the code path of one thread would read it. `WindowParser` cuts the window into chunks of 64 slots, and a `Util::ChunkPool` ([src/util/chunk-pool.h](src/util/chunk-pool.h)) hands them to its threads, the scan's own included. Each thread has a `FileRecord` of its own, and turns each slot into a `SlotOutcome`: its kind, its entry, its data state, its counters. The scan's thread takes the outcomes in record order. Only it reads the volume, changes the scan or logs. The messages of a chunk are captured (see Logging) and replayed record by record. What the attributes of a slot log when they are dropped comes with the next slot, as one thread drops them when it parses the next one. A thread MUST NOT read the volume or touch any lazy state of it: a slot that needs a read is parsed again by the scan's thread. They are a slot with an `$ATTRIBUTE_LIST` (its first pass is only the header, then it waits as before), a slot with a `$LOGGED_UTILITY_STREAM` (a non-resident `$EFS` is read), a slot the window does not serve, and a record below 16. A volume with a raw attribute callback has one thread, since the callback belongs to the caller's. The tree, the statistics, the log and the reads, the hints included, are the same whatever the count: the unit tests compare them for 1, 2, 3 and 8 threads, and the fuzz harness scans each input with one thread and with three, and aborts on a difference. The second pass has the same threads, through `WaitingParser` ([src/mft/tree.cpp](src/mft/tree.cpp)). It cuts the waiting base records into batches of 4096 and chunks of 64, and a thread parses each record whose bytes and extension records are all held, into a `SlotOutcome`. The scan's thread merges the outcomes in waiting order, replays the captured messages, and hands the data states to `DataStateResolver`. `ReadAnnouncer` runs for every record, as with one thread: the reads and the hints do not change. A record that reads stays on the scan's thread: one not held, one with unheld extension records, one with a non-resident list (`HeldRecords::Waiting` says it), and one that turns out to read. `FileRecord::SetReadRefusal()` makes a thread's `FileRecord` refuse every other read: an extension record that the source does not give, a non-resident list, a non-resident `$EFS`. The read is skipped and noted, and the thread hands the record back, whole. `HeldRecords`, `SlotBases` and the waiting list MUST NOT change once the first pass has ended: threads only read them. A count left to the scan takes threads for the second pass from 2048 waiting records on, whatever the first pass found: it reads next to nothing, so the CPU binds it even where the volume bound the first pass. Measured on a SATA SSD with `--deleted --recover`, the second pass of 338 000 records fell from 6.8 s to 5.6 s: 326 000 records parse on threads in 0.2 s, and the 11 000 with a non-resident list stay on the scan's thread. Their reads are served from the announcements, 0.4 s of wait in all. The rest of the 5.1 s is the log: 7 900 recovered list errors, written one by one to an unbuffered stderr, and `--log=console:off` removes them. A count left to the scan takes the machine's threads, up to 4, on a volume of 131 072 slots or more, and, for the first pass, only once a probe says they pay: this thread parses the first 65 536 slots while the scan times the loads of the windows (`Mft::ScanThreadsPay()`), and threads start if the loads took a fifth of the time or less. A volume read slower than one thread parses, such as a SATA disk or a hard disk, binds the scan: measured on a SATA SSD, 4 threads left the scan at the same 17.5 s and added 5 s of CPU. A volume read faster, such as a cached `$MFT`, gives a scan a third shorter. Attributes and file record headers come from `Util::SmallBlockPool` ([src/util/small-pool.h](src/util/small-pool.h)), thread-local lists of freed blocks, through a class-level `operator new` of `AttrBase<S>` and `Record::Header`: a scan makes and drops several of them for each record. The result is plain owned data, not tied to a strategy, but the scan SHOULD run on a `NoCache` volume: `FullCache` would keep the whole `$MFT` cached. `NtfsMftList` ([NTFSLibTests/examples/ntfsmftlist/main.cpp](NTFSLibTests/examples/ntfsmftlist/main.cpp), `--deleted`/`--recover`/`--threads=N`) lists its output, and never frees its tree; a damaged record is dropped when strict, kept with partial data when recovering, either way counted in `Stats().damaged`. A record is damaged when strict mode would reject something in it: an attribute that fails to parse, a cut or damaged `$ATTRIBUTE_LIST` or run list, or a failed update sequence check on some sector. The count is the same in both modes. A recovering scan knows what it salvaged because `Log::Recoverable()` counts every condition it is called for with `recover` set (`Log::Detail::RecoveredCount()`), and `FileRecord::IsSalvaged()` is true when a `ParseAttrs()` met one, the parse of an extension record included. A record with a failed update sequence check counts once, and is also in `unreadable` when strict (`FileRecord::HasFailedFixup()`), or in `in_use`, `deleted` or `extensions` when recovering. A call of `Log::Recoverable()` MUST NOT be made for a condition that strict mode accepts. With `--recover` it also prints what the change journal knows of each entry (a `~` line), and, with `--deleted`, the files only the journal names. `FileRecord::TraverseSubEntries()` is the lighter, per-directory recovery: with the volume's `recover_errors` on, it also scans the `$INDEX_ALLOCATION` blocks no index pointer reaches, capped at `max_orphan_scan_blocks`; an entry found this way is reported only if its parent reference matches.

### Namespaces

The root namespace is the macro `NTFS_BROWSER_NAMESPACE` from `<ntfs-browser/namespace.h>`. CMake generates that header from [namespace.h.in](include/ntfs-browser/namespace.h.in), with the value of the cache variable of the same name (default `NtfsBrowser`). Code MUST write `NTFS_BROWSER_NAMESPACE::` and MUST NOT spell the namespace out. The unit-test helpers live in `NTFS_BROWSER_NAMESPACE::Tests`. Only `IDiskReader`, `NtfsVolume`, `IndexEntry`, `Filename` and `VolumeOptions` live directly in `NTFS_BROWSER_NAMESPACE`. Everything else MUST sit in a sub-namespace, whether a class, an enum, a function or a constant. A file named `<prefix>-*` (or `<prefix>.cpp`) MUST live in folder `<prefix>/` under the matching namespace: `attr-*` in `Attr`, `file-*` in `Io`, `mft-*` in `Mft`, `log.cpp` in `Log`. Namespaces follow the application domain, never the kind of C++ entity: there is no namespace for enums. They are `Attr` (attribute wrapper classes `AttrBase`, `Attr::Type`, `Attr::Mask`, `Attr::HeaderCommon`, `Attr::RawCallback`, slot helpers, flag bits), `Data` (on-disk layouts and their helpers), `Record` (file record header, and the `Record::CarvedName` names carved from record slack), `Io` (`FileRecord`, `FileReader`, `Win32DiskReader`), `UpCase`, `Utf`, `Util`, `Mft` (`MftTree`, `Mft::Idx`, file reference helpers), `Volume` (boot sector geometry decoded from the BPB: `Volume::Geometry`, `Volume::ParseBootSector()`), `Cache` (`Cache::Strategy`, `Cache::View`, `Cache::Stats`, `Cache::BlockCache`), `Alloc` (cluster allocation from `$Bitmap` and `$BadClus`: `Alloc::ClusterState`, `Alloc::DataState`, `Alloc::Extent`, `Alloc::SpaceSummary`, `Alloc::BadClusters`, and the internal `Alloc::ClusterBitmap` and `Alloc::BadClusterList`), `Usn` (the change journal: `Usn::Record`, `Usn::Journal`, `Usn::Reason`, `Usn::default_max_records`, `Usn::unlimited_records`, and the internal `Usn::RecordScanner` and `Usn::LoadJournal()`), `Log` (levelled entry points `Log::Trace`... beside the public configuration), `Efs`, `Lznt1`. A constant used by one `.cpp` goes in its anonymous namespace. A constant tied to one class is a static member of it.

### Directory structure

- `include/ntfs-browser/` — public API headers. These are what consumers of the library include.
- `src/` — implementation, plus internal-only headers not exposed publicly: `src/data/` (on-disk struct layouts and their bitflag enums, namespace `Data`: boot sector BPB, file record header, index block/entry, run entry, attribute headers and bodies), `src/attr/` (attribute flag bits), `src/cache/` (the `FullCache` block cache and `Cache::View`, namespace `Cache`), `src/record/` (file record header validation and fixups, and the slack carver), `src/volume/` (boot sector geometry, namespace `Volume`), `src/efs/` (EFS: `$EFS` parser, FEK, sector ciphers for both backends, Windows key providers), `src/usn/` (the change journal: record scanner and loader, namespace `Usn`; the on-disk record layouts are in `src/data/usn-record.h`). Tests include from `src/` directly (see `NTFSLibTests/unit-tests/CMakeLists.txt`), to reuse these on-disk struct layouts when building fake images, rather than duplicating byte offsets.
- `NTFSLibTests/` — `unit-tests/` (Catch2, one folder per namespace), `tools/` (the `NtfsFakeImage` and `NtfsTestDiskReaders` static libraries the tests and `NtfsFuzzer` link, the `NtfsDeviceAccess` library the samples and `NtfsCompare` share, plus `ntfscompare`), `fuzz/` and `examples/` (the older MFC-based sample/demo apps).
- The repository holds no copy of Microsoft's compression spec, [MS-XCA] (LZNT1 included). It is online: <https://learn.microsoft.com/openspecs/windows_protocols/ms-xca/>. The LZNT1 tests cite its sections.

### Callbacks

Two callback mechanisms exist. `Attr::RawCallback` (installed via `InstallAttrRawCB` on `NtfsVolume`/`FileRecord`) fires during raw attribute parsing; it can veto or discard an attribute before it's wrapped. `FileRecord::AttrsCallback`/`FileRecord::SubentryCallback`/`FileRecord::StandingCallback` are post-parse traversal callbacks (`TraverseAttrs`, `TraverseSubEntries`, `TraverseSubEntriesWithStanding`) for consumer code, matching the style used in the sample apps.

### Fuzzing

Both fuzzers drive the same path — open a `NoCache` volume, parse the root `FileRecord`, `TraverseSubEntries` — and treat thrown C++ exceptions as "handled" (bad input rejected), leaving only genuine crashes (access violations, CRT aborts) to escape as real findings:

- `NtfsFuzzer` ([NTFSLibTests/fuzz/main.cpp](NTFSLibTests/fuzz/main.cpp), Windows-only) feeds an endless RNG-backed byte stream through `SequentialDiskReader`; a SEH handler around each iteration catches crashes and prints the seed to repro with `NtfsFuzzer --seed <seed>`.
- The fuzzing logic lives in the `NtfsFuzzCore` static library ([NTFSLibTests/fuzz/fuzz-core.cpp](NTFSLibTests/fuzz/fuzz-core.cpp), `NtfsFuzz::FuzzTestcase()`). `NtfsFuzzerAfl` and the regression test both call it. The test calls it in-process, so no child process runs.
- `NtfsFuzzerAfl` ([NTFSLibTests/fuzz/afl-main.cpp](NTFSLibTests/fuzz/afl-main.cpp)) is a classic afl-gcc/afl-g++ file-input harness (`NtfsFuzzerAfl <path>`, or `afl-fuzz -i in -o out -- ./NtfsFuzzerAfl @@`); it loops the input via `LoopingDiskReader` instead of generating fresh bytes, and builds on Linux too (portable C++, no SEH). After the root walk it parses the root again, then records 0, 3, 6 and 10, with every attribute type, calls their getters and reads each attribute's data. A key provider of its own stands in for the certificate store: it returns the wrapped FEK stored in `$EFS` as the already decrypted FEK, so an input picks its own cipher and key. It then scans the `$MFT` with `MftTree`, which stops after the first few thousand records, and calls the volume getters and raw attribute callbacks. It runs each input once per cache strategy, and once per strategy for each `VolumeOptions` mode (strict, fully recovering, and strict under a one-block `max_cache_bytes` ceiling; the last runs `FullCache` only, since `NoCache` ignores it). `--inject-read-failures` adds one run per strategy per mode for each of the first 16 `ReadInto()` calls, each failing that one read. It reaches the disk-read error paths, but multiplies the run time by roughly 51 (3 modes x (1 base + 16 injected)) per `FullCache` run. AFL runs MUST NOT pass it.
- An input is the byte stream the fuzzer replays, not an image: reads ignore their address. `NtfsFuzz::ProbeOnce()` runs the first pass of `FuzzTestcase()` over any `IDiskReader`, so a `RecordingDiskReader` around a synthetic image records such a stream. The `alloc_bitmap_*` inputs were made that way, from the cluster bitmap fixtures (a forged volume or bitmap size, a cut or fragmented run list, a short resident bitmap); `FuzzTestcase()` also queries the bitmap, the bad list and the data state of every stream it parses. The `bad_clusters_*` inputs come from `PutBadClusterList()` (a cut run list, extents past the volume, overlapping or out of order, a forged size, no `$Bad` stream, odd attribute flags). The hidden test case `write the bad cluster fuzz inputs` (`NTFS_BROWSER_FUZZ_INPUT_DIR`, tag `[.write-fuzz-inputs]`) rewrites them: it also cuts bytes 512 to 4096 out of the recording, since the volume reads its boot sector in 4096 bytes and `LoopingDiskReader` moves the stream by only 512 after that first read. The `usn_journal_*` inputs come from `PutUsnJournal()`: a forged or zero length, a name past its record, a V4 record, mixed versions, a cut tail, a USN that is not its offset, a sparse head. The hidden test case `write the usn journal fuzz inputs` writes them, recording with the volume recovering, since only then does it read the journal. `FuzzTestcase()` also feeds the input straight to `Usn::RecordScanner`, from each of 8 alignments, whole and cut in two. The `record_slack_*` inputs come from `PutRecordSlack()` (candidates on top of each other, a name cut by the end of the record, stale terminators and an impossible parent): the hidden test case `write the record slack fuzz inputs` writes them with the volume recovering and showing deleted items, and `FuzzTestcase()` reads every carved name of a scan and of each probed record.
- A recorded input MUST replay in step on every build, so the read order of `FuzzTestcase()` MUST NOT depend on the build. `ProbeVolume()` therefore parses the root once per cipher backend slot (CryptoPP, then BCrypt) whether the build has the backend or not: a refused `SetEfsCipherBackend()` leaves the previous one in place. `FuzzOnce()` also scans the input twice, over readers of its own, with one thread and with three: the digests of the two trees MUST be equal, or the process aborts. A recorded input only reaches the second pass of that scan if it was recorded from the scan itself, through `NtfsFuzz::ProbeScanOnce()` and `Tests::FuzzInputs::WriteRecordedScanInput()`: the main probes read in another order. The `scan_threads_waiting_*` inputs are such recordings. A probe added later MUST run after the others (`ProbeUserRecords()` and the search for a name outside the BMP come last), or it moves the reads of every recorded input. The later families come from the hidden test cases of [NTFSLibTests/unit-tests/fuzz-regression/](NTFSLibTests/unit-tests/fuzz-regression/), which record through `Tests::FuzzInputs::WriteRecordedInput()` ([fuzz-input-writer.h](NTFSLibTests/unit-tests/fuzz-regression/fuzz-input-writer.h)): `usn_tree_*` and `usn_loader_*` (journal records that name entries of the tree, files only the journal names, a journal missing its `$Extend` entry, record or `$J`, a cut run list), `usn_scanner_damaged_names` (written as a file, not recorded: the scanner meets it directly), `alloc_scan_*`, `alloc_bitmap_short_with_bad` and `mft_bitmap_*` (freed streams resolved in one batch, a live stream over free or bad clusters, a short bitmap, the `$MFT` bitmap kinds), `mft_scan_*` (sectors that fail the update sequence check, a fragmented `$MFT`), `scan_threads_waiting_*` (every kind of waiting base record: held, foreign, unreadable or non-resident list, freed), `attribute_list_scan_*` and `attribute_list_multi_cluster` (a file whose extension records sit on both sides of its record, one of them foreign, the same file with its list out of its record, and a non-resident list over two clusters), `run_list_*` (an empty, overflowing or cut run list) and the slack families `record_slack_name_units`, `record_slack_rejected_fields`, `record_slack_repeated_names`, `record_slack_live_names` and `index_slack_repeated_names`. The read of a failed cluster cannot be recorded, so an input never reaches a read failure by itself: `--inject-read-failures` does.
- Crashing inputs found this way get saved into [NTFSLibTests/fuzz/data/](NTFSLibTests/fuzz/data/) as a regression corpus, replayed by the Catch2 test in [NTFSLibTests/unit-tests/fuzz-regression/fuzzer-regression-tests.cpp](NTFSLibTests/unit-tests/fuzz-regression/fuzzer-regression-tests.cpp). That test runs each saved file in-process through `FuzzTestcase()` with `inject_failures` on, and checks that no exception escapes. For entries in its `expected_error_messages` table, it also checks the trace messages the run logged, captured by the test log sink, against the specific parse-error message the fix is supposed to produce. A real crash in this in-process run ends the whole `NtfsBrowserTests` binary, not just one case. The `NtfsFuzzerAfl command line` tests in the same file call `NtfsFuzz::RunCommandLine()` in-process. The console stream split stays a subprocess test (`log/logging-child-process-tests.cpp`), since it needs real standard streams.
